Navigating the Limits of Synthesis

A hardness theorem can be read as a map of the choices a practical synthesis system must make.

Dana Edwards · November 11, 2026 · Research essay

A limit is a map

A hardness theorem does more than label a problem hard. It identifies an obstacle a general method must confront, and helps show what a practical system can bound, supply, or check.

Program synthesis makes the question explicit: find a program that meets a specification. For a bounded transfer rule, for example, the system may have to choose an expression, check every admitted balance and amount, and ensure that the expression always terminates. Each of those choices can be finite, infinite, or delegated to another source of evidence.

For a basic Turing-complete imperative language, Jinwoo Kim proved that deciding this general realizability question is Σ⁰₃-complete. In the arithmetical hierarchy, that sits two quantifier alternations beyond the Σ⁰₁ halting problem. It is a result about unrestricted generality, not a measure of the practical difficulty of every synthesis task.

Read as a wall, the theorem says that no universal synthesis procedure can always decide the question. Read as a map, it exposes the choices a practical system can restrict: the candidate program, the input domain, and the execution witness.

This essay separates three kinds of claim. The theoretical claims are cited. Claims about ZAL and ZenoFCIS describe repository documentation at commit 4160086 rather than a fresh source-level execution. The proposed scaling directions and experiments are proposals, not demonstrated results.

Three quantifiers expose the unrestricted problem

In Kim's setting, the question has the form: there is a program p such that, for every input x, there is a finite run t whose output meets the specification. The decidable predicate underneath says what the run did within t steps and whether that output is acceptable.

∃p ∀x ∃t : R(p, x, t)
  • There is a program. The candidate space is unbounded.
  • For every input. The cases to cover are unbounded.
  • There is a finite run. Whether an arbitrary run terminates cannot be decided in general.

This form gives a useful design decomposition. In standard effective restrictions, making a candidate set finite, fixing or bounding the input domain, or requiring a total evaluator removes or collapses quantifiers in different ways. The table is a guide to those restrictions, not a claim that every bound always lowers the hierarchy by one level.

The upper bounds assume the remaining predicates are effectively decidable and the candidate space is effectively enumerable. Completeness for a restricted class requires a separate hardness argument.

At Σ⁰₁, a positive instance can be found by search: if a witness exists, the search eventually finds it; if none exists, the search may run forever.

With a finite candidate set, an admitted finite input domain, and a total evaluator, the decision reduces to a finite count. That is the design point used by ZenoFCIS finite-profile routes.

Finiteness makes a problem decidable; it does not make it cheap. The cost still depends on how compactly the instance is described and on the number of candidate-input checks.

The classifications in this table are unconditional. Their implications against polynomial-time algorithms depend on familiar open separations for the first two rows. Time-hierarchy theorems give an unconditional separation of exponential-time classes from polynomial time (Hartmanis and Stearns 1965).

What the theorem forbids and leaves open

Kim's result rules out completeness in its stated general setting. It does not rule out systems that work well on an explicit task family, under an explicit scope, with an explicit source of help.

In the unrestricted setting, four ambitions fail.

  • A complete decision procedure. No algorithm always decides whether the specification is realizable.
  • A complete refuter. No general procedure enumerates exactly all unrealizable requests.
  • A sample-only stopping rule. Without a specified hypothesis class or other assumption, finite examples cannot certify that a proposed rule will generalize.
  • A guaranteed counterexample loop. Guess, check, add a counterexample, and repeat can run forever in the general case.

There is a useful existence construction. If outputs can be enumerated, acceptability is decidable, and every input has an acceptable output, a selector can try outputs at run time until one passes. This shows why unrestricted relational synthesis can be easy to satisfy while still being uselessly slow.

In that qualified sense, a specification can act like a slow program. Synthesis then becomes the search for a shorter, faster, safer, or otherwise constrained program that agrees with it. Over a finite representable domain, a lookup table provides the same baseline; the work is to compress or explain it.

This motivates an interpretive lens rather than a theorem: a finished program can be viewed as search whose choices have already been fixed. A deterministic program follows those choices at run time, even when the program itself performs a search.

The remaining difficulty lives in constraints such as short and fast. The complexity of finding the smallest circuit for a fully specified Boolean table, the minimum circuit size problem, remains open.

Hirahara (2022) proved NP-hardness, under randomized reductions, for the partial version in which a Boolean truth table may contain unspecified entries. A contract that permits several outputs for an input has a related partial-information shape, but it is not automatically an instance of that problem; an explicit reduction would be needed.

Liu and Pass (2020) give a precise average-case result: one-way functions exist if and only if suitable time-bounded Kolmogorov complexity is mildly hard on average for probabilistic polynomial-time algorithms. That is narrower, and more useful, than an informal claim about every shortest fast program.

What remains open is the structure of the practical problem family.

  • The task distribution. Real requests are not sampled uniformly from all possible specifications.
  • Restricted classes. Each explicit restriction can yield a better decision procedure or a stronger scoped claim.
  • External help. A witness, invariant, proof, or human answer can turn a search problem into a checking problem.
  • Honest scope. A claim such as “for every admitted input up to this size” is weaker than universality, but fully checkable.

This is an engineering hypothesis, not a theorem: requirements written from small mental models often have structure that search can exploit. A serious system should measure that hypothesis on its own task population.

The ways through and what they cost

Every practical route through a limit supplies something so that search has less to find. The following accounting is a useful design vocabulary, not a universal law of problem solving.

Suppose candidates are tried in nonincreasing order of a normalized prior. If the desired candidate has positive prior mass p, its rank is at most 1/p. Writing b = −log₂ p gives the familiar bound 1/p = 2ᵇ: b is the candidate's surprise under that prior.

Work is bounded by trials times the cost of checking. With nonuniform checks, use total checking cost rather than one fixed cost.

Missing bits are the information the proposer or search order does not already supply. A technique can reduce the candidate space, make a check cheaper, provide a witness, or change the question to one with an explicit scope.

That vocabulary highlights four sources of help: a person, a proof, prior experience, or additional search.

A person pays in attention. A proof is paid for once and replayed. Experience is a bet that the next task resembles the tasks that supplied the prior.

The no-free-lunch theorem gives a narrow version of this point: under a uniform average over all objective functions on a fixed finite space, non-revisiting black-box optimizers perform equally in the standard setting. Useful priors win only because practical task distributions have structure (Wolpert and Macready 1997).

Levin's universal search supplies a reference ideal for suitable enumerable search-and-verification problems: it is optimal up to a multiplicative overhead under a fixed encoding. The overhead can be astronomical, and depends on the competing method's description, runtime, and verification cost. Practical systems improve by exploiting a better language, prior, and checker (Levin 1973).

IP = PSPACE shows how much checking can accomplish inside finite complexity classes: a randomized polynomial-time verifier can interact with an unbounded prover to verify PSPACE claims with bounded error (Shamir 1992). It is a useful model for checked proposals, not a way to decide arbitrary undecidable synthesis claims.

A common anatomy for checked search

Programs are one instance of a common pattern: a candidate space, a judge, and a failure report. According to the ZenoFCIS documentation, the same pattern is used for at least ten target kinds.

Three distinctions matter.

A positive claim and a negative claim need different evidence. A positive result presents one candidate for the judge to check. A negative result claims that a space was covered, so its authority depends on the coverage argument.

The documented ZenoFCIS distinction is similar: selection rests on the checker, while “no solution” also rests on complete enumeration of the admitted sketch.

Proposal independence needs an exact judge. When the judge is only a sample or a person, the search order can influence the answer. A fit to examples remains a proposal until a declared full-domain check accepts it.

Judges become more empirical as their targets become more abstract. A finite-profile program check can exhaust the admitted inputs. A representation or search-strategy assessment relies on another search or a population of tasks, so the resulting verdict needs a narrower scope.

What the documentation says about ZAL and ZenoFCIS

According to the documented finite-profile routes, ZenoFCIS explicitly bounds the candidate space, input domain, and evaluator. Within those bounds, exhaustive checking supports its stated notion of a proved result.

QuantifierDocumented boundWhat it buysWhat it costs
There is a finite runA pure, total decision coreEvery admitted evaluation terminatesLoops and effects stay in a separate shell
For every inputAn admitted finite domain of at most 65,536 inputsEvery admitted case can be runLarger ranges use a solver route with an Attested status

The documented limits are deliberate: one million candidates is about 20 bits, and 65,536 inputs is 16. Their product is at most 2³⁶ candidate-input evaluations before accounting for per-check cost or early termination.

The documentation also describes several familiar search moves already in use.

  • Supply a witness. A language model or a person proposes; the checker decides within scope.
  • Search meanings, not texts. Hole search ranges over denotations, and refuted programs can be remembered by meaning.
  • Learn from failure. A refuted proposal returns a failing region and ranked repair sites.
  • Split the problem. Decomposition reports interface counterexamples, then checks the composed result.
  • Ask the person well. A version-space question can choose an input that separates surviving meanings.
  • Guard the meta level. A lesson becomes advice only after a frozen held-out comparison with and without it.

ZAL supplies the statement against which those results are judged: it turns a person's mental model into explicit finite-model claims, together with a record of their stated authority and scope.

The documentation also describes temporal and game checks over finite models, including declared symmetries and one representative per orbit. These are documented capabilities, not claims newly tested in this essay.

That is a documented starting point. The remaining question is how to extend it without weakening the evidence carried by a result.

Proposed paths to scale checked search

The following directions are proposals, not results established here. They aim to reduce or redistribute search effort while preserving an explicit basis for checking results.

Several documented mechanisms already have that shape.

  • Programs with the same admitted table. One checked meaning.
  • Hole values with the same effect. One candidate class.
  • States related by a declared symmetry. One orbit.

A ZAL statement can play the same role. A person already groups cases under concepts such as an account, enough balance, or too early. If that grouping preserves the property being checked, a machine can search classes rather than individual cases.

Each direction names the judge and the condition that would make the reduction safe.

1. Certificates for unrealizability beyond a fixed sketch

A negative result can sometimes cover every expression in a grammar, rather than only a fixed size bound. For example, AND and OR alone generate only monotone Boolean functions, so they cannot express NOT over ordinary Boolean inputs. The certificate is a relation preserved by every permitted terminal and operator but not by the target.

For total operations on one finite carrier, the Pol–Inv correspondence says that such a finite-arity separating relation exists whenever an operation lies outside the clone generated by the vocabulary (Geiger 1968; Bodnarchuk et al. 1969). A typed language with traps or partial operations needs its own verified bridge. Unrealizability logic offers a proof system for related claims over program grammars (Kim, D'Antoni and Reps 2023).

2. Exact abstraction for restricted fields

An equality-only identifier field may admit a finite set of representatives, but only after a data-independence argument covers the program, specification, environment, named constants, generated literals, and relevant equality patterns. Under those conditions, unused identifiers can be permuted without changing the outcome (Wolper 1986).

Timed automata give an instructive analogue: Alur and Dill construct finitely many regions from permitted guards, constants, resets, integer parts, and fractional-order information. It is not a general theorem for ordinary order-only fields. The proposed ZenoFCIS route would require a syntactic usage check and a separately checked abstraction lemma.

3. Promote solver results with proof checking

A checked proof can strengthen a solver result relative to its encoding, proof checker, and bridge from encoding to contract. The documented distinction is sensible: a bare unsat response is Attested, while a proof-carrying result could support a stronger status. Solvers can emit proofs, and small independent proof checkers exist, including formally verified ones (Tan, Heule and Myreen 2021; Andreotti, Lachnitt and Barbosa 2023).

Proof checking can remove the solver from the trusted base, but it does not remove the encoding or the contract-to-encoding bridge. Those remain proof obligations.

4. Test a cost ledger

For a fixed counted candidate space, a stage that reduces the surviving set from S to S′ removes log₂(|S|/|S′|) bits. Dividing that quantity by measured checking work could become a useful local metric; it is not a universal currency until it predicts useful choices on held-out tasks.

The same ledger can make assumptions visible. A binary human answer supplies at most one answer bit, but the statement may also depend on assumptions supplied by the question design and language.

For ZAL, a planted edit that changes no case a reviewer confirmed may expose one such assumption. It is a candidate next question, not yet a result.

5. A fixed-share portfolio

With explicit work accounting, several deterministic strategies can share one budget. A fixed-share dovetailing schedule gives a multiplicative overhead determined by the share assigned to the best strategy, echoing Levin's portfolio argument (Levin 1973).

Metering supplies the work bound. Determinism and replay still require deterministic sub-strategies, recorded seeds or orders, and a deterministic scheduler.

6. Ask proposers for lemmas as well as answers

Short proposals with exact judges can be unusually valuable. An accepted invariant can exclude a region, and an accepted abstraction lemma can cover a large range only when its stated conditions have been checked.

A language model can propose invariants and abstraction lemmas as candidate artifacts, just as it can propose programs. A graded failure signal may help guide proposal search, but acceptance still belongs to the exact judge (Romera-Paredes et al. 2024).

That separation permits aggressive proposing without weakening the acceptance rule.

Searching for better search

A faster search is itself a target for search, so it needs a judge of its own. Certified failures can safely shrink a candidate space; successful patterns can shorten later proposals.

The documented system already has both memories: refuted meanings on one side, and checked rules and lessons on the other.

Both memories make claims about future searches. The judge required depends on what the claim could break.

KindExamplesWhat it could affectWhat it needs
AdviceCandidate or input order, prior, schedule, question choiceSearch timeA recorded receipt and measurement

Advice is correctness-neutral only when every chosen candidate is rechecked. It must still be recorded: an unrecorded order cannot be replayed or assessed.

Skips are where a negative claim is won or lost. Every skipped region needs a reason that a small independent judge can check. Proof-logging SAT workflows provide the relevant model: an untrusted search procedure emits an artifact checked independently.

Replacements point the system at itself. For a fixed finite contract, a replacement evaluator can be checked for equality with the original across the admitted domain. Outside that domain, the equality claim needs its own proof method.

Each speed-up should therefore be treated like any other candidate: a space, a judge, and a failure that teaches.

Two cautions apply.

More knowledge can make search slower. A macro may shorten some answers while widening each choice. Minton (1990) measured learned rules that cost more to match than they saved.

The documented promotion rule is a pragmatic guard: promote a lesson only when the held-out comparison finds no task worse and at least one better. Verified macros should come before larger learned libraries.

The meta level can overfit. A strategy tuned on a few tasks has learned those tasks. Freezing the strategy before held-out evaluation limits that risk without eliminating it.

The documented strategy grammar has five sequences. It should grow no faster than the task population that can assess it.

Four falsifiable experiments

These experiments are ordered by implementation cost. Each has a defined success condition and can return a useful negative result.

  1. A bits ledger. From episode records, compute candidate shrinkage per unit of checking work for each stage and owner question. It succeeds only if the ranking predicts which lessons pass a held-out assessment. Otherwise, drop the metric.
  2. An invariant for one known negative result. Take a sketch reported unrealizable by the documented loop. Search a small relation space for one preserved by the vocabulary and violated by the goal. It succeeds if the checked certificate costs much less than exhaustive enumeration.
  3. A restricted-field abstraction. Take a contract with a genuinely restricted field. Compare every reduced-domain verdict with a trusted full-range route. A single disagreement refutes the proposed lemma before anyone relies on it.
  4. One checked solver proof. For a pinned inductive claim, ask the solver for a proof and run an independent checker. Count accepted proofs and their cost. A low acceptance rate is still a result: it identifies fragments that need another route.

The second experiment needs a control in the same style: a sketch known to be realizable must never receive a negative certificate. If it does, the certificate judge is wrong.

The table distinguishes what is established by cited theory, what is documented in the repository, and what this essay proposes.

This analysis has four limits.

Documentation boundary. The ZenoFCIS discussion reads repository documentation at commit 4160086, not the Rust source. A described omission may already be implemented.

No new execution. None of the proposals was run for this essay because the pinned Rust toolchain could not be installed in the writing environment.

Clone-theory boundary. The finite-domain guarantee concerns total operations on one finite carrier. The typed, trapping case needs a separate construction.

Ledger boundary. Bits are exact only after fixing a counted space and a prior or elimination measure. Using them to price stages and questions is a proposal.

The limits do not tell us to stop searching. They tell us what must be paid for: an explicit bound, a witness, a proof, usable structure, or a person's attention. A trustworthy synthesis system records which of those supports each answer, and what scope that support buys.
